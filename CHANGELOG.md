# Improvement Changelog

| Stage | What was tried and why | Evidence | Decision / learning |
|---|---|---|---|
| Baseline | Documentation and tool-catalog review without executing the server. | Generated by `npm run baseline`. | Establishes a safe, low-cost starting point but cannot see hidden runtime behaviour. |
| Iteration 1 | Added static source inspection for process, filesystem, environment and network primitives. | Generated findings include file evidence. | Kept; improves coverage before execution, but can over-report capability rather than actual use. |
| Iteration 2 | Added Docker sandboxing and a protocol probe. | Runtime traces and probe results in `reports/evaluation.json`. | Kept; enables observation while refusing unsandboxed execution. |
| Iteration 3 | Added a deterministic evidence verifier and fixed fixture ground truth. | Evaluation compares expected findings to reported findings. | Kept; makes the improvement measurable and reproducible. |
| Removed experiment | Unrestricted host execution was considered for faster testing. | It would expose host files, credentials and network. | Removed; security testing must fail closed when the sandbox is unavailable. |
| Real-repository check | Ran the documented `weather-server-typescript` stdio server from the public MCP quickstart resources in the Docker sandbox. | Protocol initialized; `get-alerts` and `get-forecast` discovered; `api.weather.gov` network attempt traced. | Kept as an example of evidence-backed review. The network signal is expected functionality under the repository's documentation, but must be explicitly allowed by a deployment policy. |
| Quarantine preparation | Added a Docker-only fetch/install/build path for untrusted public repositories. | Clone and dependency steps are isolated; lifecycle scripts are disabled; build is offline and commit-pinned. | Kept; prevents the preparation workflow from executing repository code on the host. |
| Vulnerable/patched comparison | Added a shell-interpreted execution signal for `execSync` and excluded ordinary SDK method calls from that specific signal. | Kubernetes `v2.4.9`: 23 shell-execution evidence lines; `v2.5.0`: 0. Synthetic recall stayed 7/7 with zero false positives. | Kept; makes the known command-injection regression visible while preserving a less noisy generic process-capability signal. |
| Runtime process refinement | Captured operation, executable, argument array and shell status; added an explicit executable allowlist and lowered direct non-shell calls to review-level signals. | With `kubectl` approved, `v2.4.9` produced 14 confirmed shell attempts; `v2.5.0` produced 0. The patched version recorded one approved `kubectl` call and one medium `helm` review item. Synthetic recall remained 7/7 with zero high-risk false positives. | Kept; separates dangerous shell construction from an MCP server's expected use of a fixed executable. |
| Evaluation integrity | Changed scoring to match each expected finding only against its own fixture; excluded generated, lock, test, documentation and CI files from static source scanning; made unverified capabilities review-level. | A regression test proves a finding in a safe fixture cannot satisfy another fixture. Final per-case evaluation remains 7/7 recall, and every safe fixture has zero unexpected high-risk findings. | Kept; the metric now measures the claimed behavior without cross-case credit or capability-only high-risk noise. |
| Submission privacy | Replaced absolute host paths in generated targets and Docker evidence with portable labels. | A repository-wide scan finds no host username or absolute home-directory path outside dependencies/build output. | Kept; submitted evidence remains reproducible without disclosing the development machine path. |

## Main failure mode

Static review can identify a capability without proving that the capability is exercised on a particular path. Dynamic probing increases confidence, but safe example inputs cannot cover every branch.

## Hot take

For MCP auditing, the most valuable signal is not a single risk score. It is the shortest path from a reported risk to reproducible evidence showing exactly what the server did.
